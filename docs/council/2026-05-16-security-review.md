# Security Council Review — 2026-05-16

**Reviewer role:** Security council member, read-only audit
**Codebase:** `D:\accountant` (Phase B mid-flight)
**Scope:** Pre-deploy gate for the first user-data landing event.
**Verdict:** **DO NOT ship to a live audience until the Critical items below are closed.** The current
codebase is structurally sound (RLS at two layers, AAD-bound AES-GCM, real cron auth, dedicated
service-role pool) but ships several deferred items that are blockers, not nice-to-haves, the moment
real PII or money flows through it.

---

## 1. Executive summary

1. **Envelope encryption is the marketing copy, not the implementation.** Every ciphertext column in
   chunks A + B (`clients.email/phone/notes_ciphertext`, `users.dob/national_id_ciphertext`,
   `receipts.ocr_text_ciphertext`, `processor_sync_credentials.api_key_ciphertext`, planned filings
   ciphertexts) is encrypted **directly under the master KEK**. No code generates DEKs, no code
   wraps them. The Privacy-Authority compliance bullets in
   `docs/runbooks/il-privacy-registration.md` § 8 currently describe a system that does not exist.
   Either ship envelope encryption before the first PII lands, or rewrite the runbook to claim what
   the code actually does.
2. **Step-up auth is entirely absent** (`lib/auth/stepUp.ts` deferred). `POST /api/account/delete`
   accepts a password re-check via `auth.api.signInEmail` and that's it. Every operation Plan v4 §
   Risk #10 + § 7.1 lists as step-up-protected (invoice issuance, business updates, processor-credential
   decryption, accountant-engagement claim, password change, MFA disable, account deletion) is either
   ungated or gated only by ambient session + a same-site=lax cookie. **This is the single highest-
   blast-radius gap in the codebase today.**
3. **Five secrets pasted in chat or generated by Claude have no rotation gate.** The runbooks document
   the rotation procedure; no migration, no boot check, no CI lint forces it. A deploy from the
   current `.env.local` to Vercel without manual diligence ships compromised credentials. The
   `selfTest.ts` boot gate could enforce a "this KEK has been ack'd as rotated post-chat-exposure"
   stamp — it does not.
4. **Turnstile silently disables when `TURNSTILE_SECRET_KEY` is unset.** `lib/auth/better.tsx:167-169`
   conditionally adds the captcha plugin only if the env var is present. A missing env in production
   means signup runs unprotected — no warning, no boot failure. `lib/env.ts:36-38` marks the
   secret optional. There is no pre-deploy gate that rejects production builds with the secret
   missing.
5. **Logging is mostly clean but contains real-world hazards.** No OTPs or verification URLs are
   ever logged. However: `lib/auth/better.tsx:99-103, 156-162` logs the recipient email on Resend
   failure; `lib/email/client.ts:136-141` logs the recipient email in skip-mode; the
   `account-purge` cron logs aggregate counts but not user IDs (good). The email leaks are
   defensible during dev but constitute PII in production logs once Sentry/PostHog ingest them.

## 2. Critical — must fix before any user data lands

### C-1. Envelope encryption is unimplemented despite the data model
**Code:** `db/schema/ops.ts:139-157` (table exists), `lib/security/kek.ts`,
`lib/security/encryption.ts:93-108`, `app/[locale]/(app)/clients/actions.ts:55-67, 103-115` (writes
ciphertext using `getKek()` directly).
**Attack vector:** Master KEK compromise (rotation, env leak, deployment-history exposure)
instantly decrypts every PII column ever written; no per-row crypto-erasure path exists, so the
Plan v4 Risk #7 right-of-erasure-via-DEK-destruction mechanism **does not work today** — the only
way to "destroy a key" is to rotate the master, which also destroys everyone else's data.
**Recommended fix (ordered):**
1. Land `lib/security/dek.ts` with `generateDek(purpose) → {id}`, `unwrapDek(id) → Buffer`,
   `retireDek(id)`. Persistence via the existing `data_encryption_keys` table; KEK wraps with the
   same AES-GCM/AAD machinery (`{table:'data_encryption_keys', column:'wrapped_dek', rowId:<dek_id>}`).
2. Migrate `encryptStringWithKey` callers to a `encryptColumn({purpose, …})` helper that resolves a
   DEK by purpose. Purpose naming: `user:<appUserId>:pii`,
   `business:<businessId>:client_contact`, `business:<businessId>:processor_credential`,
   `business:<businessId>:receipt_ocr`. The `account-purge` cron already assumes this naming
   convention (`user:<appUserId>:%`) — landing it before the cron does its first sweep is the
   forcing function.
3. Bulk re-encrypt Phase A + B rows under DEKs before letting any non-test user sign up. Currently
   feasible — no production users.
4. Update `il-privacy-registration.md` § 8 quotable bullets to reference the actual deployed key
   hierarchy.

### C-2. Step-up auth has no implementation; sensitive ops are session-only
**Code:** missing `lib/auth/stepUp.ts`; affected routes —
`app/[locale]/(app)/businesses/actions.ts:130-204` (updateBusiness updates VAT status, regulator-facing),
`app/[locale]/(app)/clients/actions.ts:123-162` (updateClient writes encrypted PII),
`app/[locale]/(app)/transactions/actions.ts:124-153` (updateTransaction can rewrite historical money flows),
`app/[locale]/(app)/ledger/actions.ts:40-108` (createJournalEntry can post into prior periods if
`app_period_is_closed` is not consulted — and **no app code consults it**),
`app/api/account/delete/route.ts:40-122` (only re-asks for password — not a hash-bound proof),
future processor-credential decryption, future accountant-engagement claim.
**Attack vector:** A stolen-cookie attacker with no password and no MFA challenge can: drain bank
ledgers via fabricated transactions, retroactively rewrite VAT status to fraud-relevant values,
delete the account, decrypt processor credentials (once that decryption surface ships).
**Recommended fix:**
1. Land the registry + payload-hash binding per Plan v4 § Risk #10: `requireFreshSession({op,
   payloadHash, maxAge: 300})`. Payload hash MUST cover the invariant fields (e.g. for invoice
   issuance: `business_id || invoice_type || sequential_number || total_minor || issue_date`) so a
   step-up grant for invoice X cannot be replayed for invoice Y.
2. Gate every server action listed above on a step-up check **before** Phase B.2 ships. Today the
   gate is missing on actions that are already live in the (app) tree.
3. Add `auth_events` rows of type `step_up_grant` / `step_up_deny` on every challenge — schema
   already supports them (`db/schema/ops.ts:48-70`).

### C-3. `app_period_is_closed` is defined but never consulted
**Code:** `db/migrations/0005_rls_layer2.sql:19-35` (helper present); zero callers in
`app/**/*.{ts,tsx}` or `lib/**/*.ts`.
**Attack vector:** A logged-in owner (or attacker with the owner's cookie) writes a `journal_entries`
row dated inside a closed fiscal year. The ledger trigger (`app_assert_journal_balance`) only checks
debit/credit balance; it does not check period closure. Plan v4's § 5.2 "Year-end close is
immutable" claim is currently false.
**Recommended fix:** `app/[locale]/(app)/ledger/actions.ts` must call
`SELECT app_period_is_closed(${businessId}, ${entryDate})` inside the transaction before INSERT.
The same check belongs in `transactions/actions.ts` update + delete paths since
`journal_lines.entry_date` is derived from those.

### C-4. Pre-deploy gate for unrotated secrets does not exist
**Code:** `docs/runbooks/vercel-env-setup.md` documents rotation as a *human pre-flight checklist*.
`handoff.md` § SECURITY lists the five flagged secrets but no CI/test/boot logic enforces them.
`lib/env.ts:64-83` accepts the values blindly. `lib/auth/selfTest.ts` validates the KEK *shape* but
does not validate its *provenance*.
**Attack vector:** A developer (or AI agent) deploys to Vercel with the local `.env.local` values
intact. Three of those secrets (Neon password, Resend, Turnstile) live in chat transcript and may
have been retained by the AI platform; two (BETTER_AUTH_SECRET, DATA_ENCRYPTION_KEY) were generated
by a model and exist in transcript context. **Anyone with that transcript reads/forges sessions,
sends as us, and bypasses captcha.**
**Recommended fix:** Add a `scripts/lint-secrets-rotated.ts` gate that:
- Reads a checked-in `docs/security/rotation-stamp.json` containing SHA-256 of the production
  Vercel-env values for each of the five secrets (the stamps, not the values).
- Refuses the build if any stamp matches the original chat-exposed value's hash (stored as
  forbidden-list in the same file).
- Wired into `next.config.ts` via a build-time `assert()` before `next build` is invoked, or into a
  Vercel build command pre-step.

Less aggressive alternative: a one-time `docs/security/rotation-receipts/2026-05-{16,17,...}.md`
file the human commits when each secret rotation is verified by an OOB channel. The repo blocks
deploy if any of the five receipts is missing.

### C-5. Turnstile silently disabled in production when secret missing
**Code:** `lib/auth/better.tsx:15, 167-169` — conditional plugin inclusion.
`lib/env.ts:36-38` — secret is `optionalNonEmpty`.
**Attack vector:** A misconfigured production deploy with the Turnstile secret missing accepts
signup from any source — bot ring, credential-stuffing run, mass abuse generator. The captcha check
is the only signup-rate-limit gate today (Better Auth's built-in limiter is per-IP and trivial to
defeat from a botnet).
**Recommended fix:** In `lib/auth/better.tsx`, replace the conditional with a hard assertion when
`env().NODE_ENV === "production"`:
```ts
if (env().NODE_ENV === "production" && !turnstileSecret) {
  throw new Error("Turnstile secret missing in production — refusing to boot");
}
```
Then put `TURNSTILE_SECRET_KEY` and `NEXT_PUBLIC_TURNSTILE_SITE_KEY` in `lib/env.ts` as required
(not `optionalNonEmpty`) once production-gated. `selfTest.ts` is the right home for this assertion.

### C-6. Client encrypt-then-update race exposes plaintext column on partial failure
**Code:** `app/[locale]/(app)/clients/actions.ts:80-117`. The INSERT writes plaintext columns
(`legal_name`, `vat_id`, address) and leaves `email_ciphertext/phone_ciphertext/notes_ciphertext`
NULL. The second statement encrypts using AAD `{rowId: newId}` and UPDATEs the ciphertext columns.
**Attack vector:** Two concurrency / failure cases:
1. The transaction commits the INSERT but the connection drops before the UPDATE runs (postgres-js
   handles transactions atomically — *if* the wrapping `tx` rolls back on throw — but the pattern
   relies on `withUser` doing its job; a transaction commit between the two statements would leak
   plaintext). Verify the entire callback runs in a single `BEGIN…COMMIT`. (Spot-checked
   `lib/db/withUser.ts:17-26` — it uses `db.transaction(async (tx) => …)` which is correct, so the
   atomicity is intact. **This sub-case is OK.** The remaining sub-cases are not.)
2. **Form bug or attacker replay**: an UPDATE-without-preceding-INSERT where the existing row has
   ciphertext bound to the *old* rowId via AAD, but the UPDATE recomputes ciphertext with the
   *current* id — this is fine (AAD is bound to *current* row id either way). But if a row gets
   re-keyed during AccountantEngagement reassignment or business merge, the AAD may stale-bind.
   None of those flows exist yet; flag for chunk D.
3. **`encryptStringWithKey` is non-deterministic (fresh IV)** — but the AAD is the same — so a
   re-encrypt of unchanged plaintext produces different ciphertext, which is correct. Document
   that updates always re-encrypt all three ciphertext columns even if only one changed (line 137-139
   does this). **This is intentional but `updateClient` reads input.email *from the form*, so if
   the form doesn't echo back the existing encrypted email, it becomes NULL on save.** Verify the
   ClientForm carries plaintext through the round-trip — if not, every edit silently drops PII.

**Recommended fix:**
- Sub-case 3 is the real one. Either: (a) the form must echo plaintext (requires decrypt-on-load,
  not yet implemented), or (b) the action must `COALESCE` against existing ciphertext and only
  re-encrypt provided fields. Today neither happens; first user who edits a client loses their
  contact data.

## 3. High — must fix before launch

### H-1. `chart_of_accounts` standard-code policy allows app_user to bypass via NULL business_id?
**Code:** `db/migrations/0005_rls_layer2.sql:201-230`. SELECT policy: `business_id IS NULL OR
app_user_can_access_business(business_id)` — correct (every signed-in user reads standard codes).
INSERT/UPDATE/DELETE policies all require `business_id IS NOT NULL AND
app_user_owns_business(business_id)` — also correct. **Result: the standard set is read-only to
app_user; mutations only allowed for the business-scoped subset.** No leak found.
**However:** `GRANT SELECT, INSERT, UPDATE, DELETE ON chart_of_accounts TO app_user` combined with
the WITH CHECK on inserts means an app_user attempting to insert a standard (`business_id = NULL`)
code gets a policy violation rather than a permission denial. That's defensible.
**Finding:** no leak, but the policy could be tightened by adding an explicit `WITH CHECK (business_id
IS NOT NULL)` row-level CHECK so the failure mode is `42501 insufficient_privilege` instead of
`23514 check_violation`. Cosmetic; not blocking.

### H-2. `invoice_sequence_audit` write policy lacks `outcome` constraint
**Code:** `db/migrations/0005_rls_layer2.sql:371-381`. Policy:
`app_user_owns_business(business_id) AND actor_user_id = app_current_user_id()`.
**Attack vector:** A signed-in owner can insert a `committed` row for an attempted_sequence number
that was actually rolled back, masking a gap. Conversely, the policy allows inserting `rolled_back`
rows for invoices that *did* commit, polluting the no-gap audit log. The audit log is the
"explanation" we owe ITA for sequence gaps; if it lies, the explanation is worthless.
**Recommended fix:** The audit row should only be writable by trusted application paths, not
ad-hoc. Two options:
1. Move audit writes to a SECURITY DEFINER helper (`app_record_sequence_attempt(...)`) callable by
   app_user but with hard-coded outcome validation against `invoices` state at call time.
2. Add a trigger that rejects INSERT if `outcome = 'committed'` but no matching invoice exists,
   and if `outcome = 'rolled_back'` but a matching invoice does exist.
Either way, the policy as written cannot be the only line of defense.

### H-3. `bank_statement_imports.file_blob_url` is unencrypted
**Code:** `db/schema/money-flows.ts:163-197`, column `fileBlobUrl: text("file_blob_url")`.
**Attack vector:** Vercel Blob private store URLs are only useful with the auth context (per
`docs/runbooks/backup-restore.md` § 2.4), so the URL itself is not enough to fetch — but if a Blob
URL containing a tokenised path leaks via DB exfil + a credential set that has Blob read access,
the attacker fetches the user's bank statement (which has account numbers, balances, vendor names).
**Recommended fix:**
- Confirm the Vercel Blob private-store path *does* require an authenticated function call to
  resolve, not a path-derived auth token.
- If it does: the URL is sufficiently opaque. Document this in `docs/adr/`.
- If the URL embeds a long-lived secret token: encrypt the column with AAD =
  `{table:'bank_statement_imports', column:'file_blob_url', rowId:<id>}`.
- The same critique applies to `receipts.file_blob_url`, `businesses.logo_blob_url`,
  `businesses.signature_blob_url`, `financial_statements.file_ciphertext` (already ciphertext —
  good).

### H-4. `business_vat_status_history` has no UPDATE/DELETE policy and no `app_user` revocation
**Code:** `db/migrations/0003_rls_layer1.sql:108-118`. Append-only by policy omission: SELECT +
INSERT only. The schema does not include `updated_at`. Good design.
**However:** `GRANT SELECT, INSERT ON business_vat_status_history TO app_user` — note no
`UPDATE, DELETE` — means an app_user UPDATE/DELETE fails at the GRANT layer (`42501`). This is
correct behaviour. **But** `app/[locale]/(app)/businesses/actions.ts:179-184` issues an
`UPDATE business_vat_status_history SET effective_to = …` from `withUser`. That UPDATE will fail
with permission denied. Either the GRANT is wrong, or the action is broken. The action is
silently broken; the symptom is that VAT-status transitions don't close out the prior period's
row, leaving overlapping history.
**Recommended fix:** Either (a) extend the GRANT to include UPDATE (allowing only effective_to
column mutation via a column-level grant), and add an UPDATE policy that restricts to setting
effective_to on the most recent open row; or (b) move the update into a SECURITY DEFINER helper.
The schema design is good; the wiring is broken.

### H-5. CSRF on state-changing endpoints relies on SameSite=lax alone
**Code:** `lib/auth/better.tsx:62-70`. Cookie attributes: `sameSite: "lax"`, `httpOnly: true`,
`secure` only in production.
**Attack vector:** SameSite=lax does *not* prevent a top-level navigation initiated form POST
(form GET → POST is blocked; form-method=POST initiated from a foreign top-level navigation IS
sent with the cookie). Specifically: a malicious page can `<form action="https://accountant/api/auth/
delete-user" method="POST" target="_top">` with auto-submit on user click, and the lax cookie
travels. Better Auth's built-in CSRF token (request must include `x-csrf-token` matching a cookie
value) is the actual defense — verify it is enabled (not just sameSite=lax). Server actions in Next
16 also include a CSRF check by default, but POST routes mounted under `/api/auth/*` rely on Better
Auth's check, and `/api/account/delete` is a hand-rolled POST with **no CSRF token check at all**.
**Recommended fix:**
1. Confirm Better Auth's CSRF token is set + verified by inspecting
   `node_modules/better-auth/dist/` (per repo CLAUDE.md, do NOT trust training data). If on, no
   change there.
2. `app/api/account/delete/route.ts` must require an `Origin: <BETTER_AUTH_URL>` header check or a
   double-submit token — passing the password alone is the second factor for ownership but does
   not prevent a confused-deputy attack from a malicious page that already has the password (e.g.
   a password-manager phishing page).
3. Add SameSite=`strict` for the session cookie — Better Auth supports it via
   `defaultCookieAttributes.sameSite: "strict"`. The cost is post-OAuth redirect breakage (no
   OAuth providers configured yet, so the cost is zero today). Revisit when OAuth lands.

### H-6. Sign-out cascades only the current session
**Code:** `app/api/account/delete/route.ts:102-104` does `DELETE FROM session WHERE user_id =
${u.authUserId}` — good for the delete path. But the generic `signOut()` flow (Better Auth's built
-in) revokes only the requesting cookie's session, leaving sibling devices alive. The MFA-disable
flow (not yet wired) MUST also cascade-revoke all sessions, otherwise a user who realises their
phone was lost cannot evict the phone by re-enrolling MFA.
**Recommended fix:** Wrap MFA-disable in a server action that issues
`DELETE FROM session WHERE user_id = ?` and forces re-auth on every device. Same for password
change. Same for ban.

### H-7. Stack-trace leakage on Resend errors
**Code:** `lib/email/client.ts:209-217`. Catches errors and returns `{message: err.message}` —
better than returning the full Error object, but `err.message` from `node-fetch`-style libraries
sometimes contains the request URL with embedded query strings (e.g. signed-redirect URLs from
Resend's idempotency layer). Confirm before relying on this.
**Recommended fix:** Allow-list the error strings we return to the caller. Anything else becomes
`{message: "email_send_failed"}`. The full error continues to flow into Sentry's server-side
capture (where it is acceptable).

## 4. Medium — fix in Phase F or G

### M-1. Email recipient logged on failure
**Code:** `lib/auth/better.tsx:99-103, 156-162`. The recipient email lands in `console.warn` on
Resend failure. Once Sentry/Vercel log ingestion is on, every signup-bounce drops an email into
log storage with retention that may exceed our deletion-policy window.
**Recommended fix:** Hash the email with a process-stable salt before logging
(`auth_events.ip_hash`-style). Sentry breadcrumb context is the right place for the raw email
during dev, gated by `NODE_ENV !== "production"`.

### M-2. Email skip-mode log
**Code:** `lib/email/client.ts:136-141`. Same critique as M-1 but only fires when
`RESEND_API_KEY` is unset — i.e. dev only. Production logs untouched. Lower severity but worth
hashing for consistency.

### M-3. `lookupLocaleForEmail` opens a JOIN to Better Auth's `user` table from a
user-controlled `email` string
**Code:** `lib/email/lookupLocale.ts:48-72`. The query is parameterised via
`sql\`… WHERE b.email = ${email}\`` — safe from injection. But it runs under `withServiceRole`,
which bypasses RLS, so a high-volume probe via `/api/auth/forget-password` (which calls
`sendVerificationOTP` → `lookupLocaleForEmail`) becomes an email-existence oracle by timing
difference. Today the `forgot-password` form already always shows a success view regardless of
match (`ForgotPasswordForm.tsx:26-30`), so the leak is server-side latency only.
**Recommended fix:** Constant-time the lookup or batch through a Better Auth rate limit bucket
keyed by `email_lookup:<hash>` to cap per-email probe rate. Already on the rate-limit-buckets
schema — wire it in Phase E.

### M-4. `accountant_engagements.scopes_jsonb` is unvalidated at the DB layer
**Code:** `db/schema/engagements.ts:24-30` and policy in 0003. The `scopes_jsonb` blob carries
`{invoices, filings, payroll, ledger, ai}` booleans. RLS policies on Layer 2 tables do NOT
consult these scopes — the `app_user_can_access_business()` helper returns true if there's any
accepted+non-revoked engagement, ignoring scope booleans.
**Attack vector:** An accountant engaged with `{ledger: false}` can still SELECT `journal_entries`
because the policy short-circuits the scope check.
**Recommended fix:** Either (a) drop the scopes_jsonb concept (engaged = full read), or (b) add
per-table policy variants that consult scopes via a new helper. Option (a) is faster; option (b)
is more honest if the marketing pages claim "scoped accountant access".

### M-5. Boot self-test runs only against the Node runtime
**Code:** `instrumentation.ts:14-30`. Edge runtime skips selfTest. Routes deployed to the edge
runtime (none today, but a future `/api/health` or `/api/cron/*` could be) would skip the
KEK/scrypt/AES-GCM round-trip.
**Recommended fix:** Document in `instrumentation.ts` and in `docs/adr/` that Edge runtime is
forbidden for any route handling auth, PII, or crypto. Lint-time guard would be belt-and-braces.

### M-6. `useTwoFactorRedirect` does a hard `window.location.href` to `/2fa/verify`
**Code:** `lib/auth/client.ts:26-30`. No locale prefix in the redirect — the user gets pushed to
`/2fa/verify` which next-intl will redirect to the default locale. Functionally fine; UX-wise
disrupting for a he-IL user mid-flow. Cosmetic.

### M-7. `sign-in` redirect param accepts arbitrary `redirect` query value
**Code:** `app/[locale]/(auth)/sign-in/SignInForm.tsx:17-43`. The form trusts
`searchParams.get("redirect")` and either does `window.location.assign(redirectTo)` if it starts
with `/post-auth`, else `router.push(redirectTo)`.
**Attack vector:** Open redirect — `?redirect=https://attacker.com/...` would push the user post-
auth to attacker.com. Today next-intl's `router.push` rewrites the path to be locale-prefixed
inside the [locale] tree, which mitigates this for ABSOLUTE URLs (push fails gracefully). But the
`window.location.assign(redirectTo)` branch happens only when `redirectTo.startsWith("/post-auth")`,
which is checked, so it's safe.
**Recommended fix:** Add explicit allow-list: redirect must start with `/` and not contain `:`,
`//`, or `\`. Currently the only protection is the next-intl path normalisation in the false
branch.

## 5. Low / informational

- **L-1.** `lib/security/encryption.ts` AAD is JSON-serialised. JSON serialisation in JS is
  deterministic for primitive-only objects but not for objects with key-reorderings. Today every
  call uses the same key order (`{table, column, rowId}`), so this is fine. Document the
  invariant in the file header so a future contributor doesn't introduce a key-reorder regression.
- **L-2.** `data_encryption_keys.purpose` unique partial index (`WHERE retired_at IS NULL`) is
  good. Once envelope encryption lands, an active-row-collision (two concurrent inserts trying to
  claim the same purpose) will fail at the index — handle this in `dek.ts` with `ON CONFLICT DO
  NOTHING` + read-back.
- **L-3.** Better Auth `cookieCache: { enabled: false }` is correctly set. Comment in the file
  cites the Council Security finding — keep.
- **L-4.** `lib/auth/selfTest.ts` is a solid model for what to add to it: secret-rotation stamps
  (C-4), runtime-allowlist check, Turnstile-secret-presence-in-prod (C-5).
- **L-5.** `Strict-Transport-Security` in `vercel.ts:48-51` is set to two years with `preload`.
  Confirm we've submitted to the HSTS preload list before relying on the `preload` directive in
  the wild — the directive itself does not enable preloading, only signals intent.
